1. Verdict

Yes — an accurate, cheap, fully local measurement of API-equivalent spend is available, and it can be joined to the usage percentage this widget already polls. Claude Code writes a complete per-request usage block to its JSONL transcripts; multiplying those by public list prices reproduces Claude Code's own cost figure to the cent (verified exactly, §5). A full scan of 277 MB / 448 transcripts takes 0.73 s.

But the conversion factor — "how many dollars is one percentage point of my weekly plan?" — is not a constant you can look up or hardcode. The endpoint never exposes the denominator (limit_dollars is null on this plan). A single live observation on 2026-09-21 gives ≈$8.79 per weekly percentage point → ≈$879 per full weekly window. Back-extrapolating that constant to the previous six weeks produces one impossible value (137% for the week of 08-28), so the ratio is either not stable across weeks or the limits were actually hit that week. One data point cannot tell these apart.

Therefore the design that works is self-calibrating, not hardcoded: log (timestamp, utilization%, cumulative $) on every poll the widget already makes, and fit the slope within the current window. That is robust to the constant changing, and it is the only way to answer "week over week" at all — see §10.

The ticket's worry about Claude chat sessions is measurable and currently moot. The endpoint returns a per-surface breakdown. Right now: Claude Code 94%, Cowork 6%, Chats 0%. You always know exactly how much of the week the transcripts cannot account for. See §9.

3. Where the token counts live

Claude Code appends one JSON object per line to ~/.claude/projects/<slugified-cwd>/<session-uuid>.jsonl. Rows with "type": "assistant" carry a complete message.usage block:

{
  "type": "assistant",
  "timestamp": "2026-09-21T17:32:03.190Z",
  "requestId": "req_011CfGz1xPq4bHY1apXcbySt",
  "sessionId": "...", "isSidechain": false, "effort": "high",
  "message": {
    "id": "msg_011CfGz1xsqybvM8L8LdpSgC",
    "model": "claude-opus-5",
    "usage": {
      "input_tokens": 2,
      "cache_creation_input_tokens": 10796,
      "cache_read_input_tokens": 24671,
      "output_tokens": 320,
      "output_tokens_details": { "thinking_tokens": 0 },
      "server_tool_use": { "web_search_requests": 0, "web_fetch_requests": 0 },
      "cache_creation": { "ephemeral_1h_input_tokens": 10796,
                          "ephemeral_5m_input_tokens": 0 },
      "service_tier": "standard", "speed": "standard"
    }

}

Everything needed for an exact cost is present: per-model, per-request, timestamped, with the 5-minute / 1-hour cache-write split broken out separately (they are priced differently — 1.25× vs 2× base input). Subagent traffic is in the same corpus, flagged isSidechain: true, and it is not a rounding error: in one overnight run on 2026-09-21, 1,315 of 1,506 requests were sidechains and accounted for $256 of $311.

Rows with message.model == "<synthetic>" (39 in this corpus) are locally-generated placeholders — API error notices, interrupt markers. They carry a usage block but cost nothing. Filtering by "model is in the price table" drops them for free and also fails loudly on a model ID you haven't priced, which is the behaviour you want.

4. The dedup trap — the single biggest correctness risk

Claude Code writes several rows per API response while streaming. Each has its own uuid but the same message.id and requestId, and the token fields grow across them. Forking or resuming a session copies history into a new file, so the same request can also appear under several sessionIds. In this corpus, 35,004 rows collapse to 20,204 real requests — 73% inflation if you just sum.

There are three candidate policies and only one is right. Measured over the whole corpus:

Token field naive sum first-wins per-field max ✓
input_tokens 107,492 +93% 55,65255,652
cache_creation_input_tokens 134,230,243 +121% 60,746,48360,746,483
cache_read_input_tokens 6,787,764,019 +62% 4,189,360,5974,189,360,597
output_tokens 18,298,440 +52% 5,768,891 −52% 12,055,611
The non-obvious half

First-wins dedup — the obvious fix, and what ccusage shipped for a while — silently loses 52% of output tokens. 7,317 of 20,204 request groups (36.2%) have a first row whose output_tokens is an intermediate streaming snapshot rather than the final count. The input and cache fields are identical across rows in a group; only output_tokens grows.

Correct policy: group by (message.id, requestId), take the per-field maximum. Fall back to a session-scoped key for the handful of rows with no requestId (7 rows here). This is the same conclusion ccusage reached after a 2× regression and a cross-session dedup fix.

On this machine the dollar impact of the output-token half is modest — output is 2–13% of the bill because cache reads dominate (§5) — but it is a 52% error on the one number a user would most expect to be right, and it costs nothing to avoid.

5. Turning tokens into dollars, and proving the formula

Public list prices, fetched 2026-09-21 from platform.claude.com/docs/en/about-claude/pricing. Only the models seen on this machine are listed; a real implementation needs a table it can extend, plus a loud failure for unknown model IDs.

ModelInput5m cache write 1h cache writeCache readOutput
claude-opus-5$5.00$6.25$10.00$0.50$25.00
claude-fable-5$10.00$12.50$20.00$1.00$50.00
claude-fable-5-1$10.00$12.50$20.00$0.25$50.00
claude-sonnet-5$2.00$2.50$4.00$0.20$10.00
claude-haiku-4-5$1.00$1.25$2.00$0.10$5.00

Cache reads are normally 0.1× base input. Fable 5.1 is the exception at 0.025× ($0.25/MTok, not $1.00) — a table that assumes a uniform 0.1× multiplier overcharges Fable 5.1 cache reads by 4×. Web search adds $10 per 1,000 searches on top (usage.server_tool_use.web_search_requests); web fetch is free.

The formula is provably right

Ran one request under Claude Code's own OpenTelemetry console exporter and compared its claude_code.cost.usage against the cost derived from the transcript row for the same request:

SourceUSDDetail
Claude Code, claude_code.cost.usage0.0206061 haiku-4-5, query_source: main
Derived from transcript usage × list price0.0206061 in 10, out 60, cacheRead 13,701, cacheWrite 1h 9,463
Difference0.0000000exact

Decomposing confirms it term by term: 10 × $1 + 60 × $5 + 13,701 × $0.10 + 9,463 × $2.00 per MTok. That last rate is the 1-hour cache-write price, which is only reachable by reading usage.cache_creation.ephemeral_1h_input_tokens rather than the flat cache_creation_input_tokens. Claude Code prices the 5m and 1h cache writes separately and so must we.

Independent cross-check: npx ccusage daily --since 20260918 reports $399.91 for the current weekly window against this spike's $398.99 — 0.2% apart, entirely explained by ccusage bucketing on local calendar days while the window starts at 19:00Z mid-day Friday.

Cache reads are the bill

Across the six weeks measured, cache reads are 55–87% of the list-price dollar — 87% in the current week. Output tokens are 2–13%. Any summary that leads with "tokens" without separating cache reads will mislead badly, and any modelling of how the plan weights usage has to get the cache-read term right first because everything else is noise next to it.

6. Hooks: the answer is no. OTel: the answer is yes.

The ticket asks whether Claude Code hooks can feed this. They cannot supply token or cost data. Checked every event in code.claude.com/docs/en/hooks:

EventTokens / cost?Carries transcript_path?Useful as a trigger?
StopnoyesBest fit — fires when a turn completes; hand the transcript path to a scanner
SessionEndnoyesCoarser; good for a final reconciliation
SessionStartnoyesOnly event carrying model
PostToolUse, PostToolBatchnoyesToo chatty for this
SubagentStopnoyesSubagent completion; sidechain rows are already in the main transcript anyway
PreCompact / PostCompactnoyes—
all othersnovaries—

So a hook can only ever say "something happened, here is where to look". The docs say as much: for billing/usage tracking they point at OpenTelemetry, correlated by prompt_id.

OpenTelemetry does carry it — verified live

With CLAUDE_CODE_ENABLE_TELEMETRY=1 and OTEL_METRICS_EXPORTER=console, Claude Code emits, after every API request:

  • claude_code.cost.usage — unit USD, a counter, attributed by model, query_source (main/subagent/auxiliary), session.id, and optionally effort, speed, agent.name, skill.name.
  • claude_code.token.usage — same attributes plus type ∈ {input, output, cacheRead, cacheCreation}.
  • Also claude_code.session.count, claude_code.active_time.total.
Why this spike does not recommend OTel as the data path
  • It is opt-in and prospective. Turning it on today tells you nothing about last week. The transcripts are already six weeks deep.
  • It requires the user to export env vars into every shell that launches claude, or set them globally — a real install burden for a menu-bar widget that today needs nothing but a Keychain read.
  • Collecting it means running a collector (otlp/prometheus) or scraping console output. console writes to the CLI's own stdout, which is not capturable from another process.
  • The metric payload includes user.email, user.account_id, organization.id — this repo's stated posture is that nothing sensitive is written to disk or logs. Routing it anywhere needs care.
  • It is not more accurate. §5 shows the transcript-derived figure equals claude_code.cost.usage exactly — because they compute it the same way.

OTel's real value here is as the oracle: it is Claude Code's own answer, so it is the right thing to validate a transcript-based implementation against in a test, exactly as done in §5. It is also the only source that attributes cost to skill.name / agent.name, which the transcripts do not — relevant only if per-skill attribution is ever wanted.

7. The open-source tool the ticket half-remembered: ccusage

The ticket says "there's some common open-source tool for this but I'm not sure which". It is ccusage (npx ccusage).

AspectccusageRelevance to CLU-3

Viewsdaily, weekly, monthly, session, blocks (5-hour billing windows), --json, MCP server, statusline Its blocks view is the closest existing thing to this widget's session ring

Used here as an independent check (§5) and it agreed to 0.2%. Worth keeping as a validation target rather than a dependency — shelling out to npx from a menu-bar agent would add a Node requirement to a project that currently has none, and its dedup semantics have moved repeatedly.

Both percentages are integers, so the rate carries roughly ±2%: $8.51–$8.90 per point. At this magnitude that is fine.

Session (5-hour) window — not usable

Poll5h utilizationCost in window to that instantImplied $/pp
17:34:17Z8%$1.41$0.18
17:40:26Z9%$4.03$0.45

Six minutes and $2.62 apart, the implied rate moves by 2.5×. Two causes, both structural:

  • Integer rounding. At single-digit percentages, ±0.5 pp is a ±6% error on the denominator before anything else goes wrong.
  • Server-side accounting lag. The endpoint's figure trails actual spend. The $2.62 burned between the polls barely moved the needle, which is consistent with the reading reflecting a state some minutes old.

Consequence Calibrate against the weekly window only. The session ring is for display; it is too small and too laggy to divide by.

The week-over-week picture, and the problem with it

Six weekly windows of transcript cost, bucketed on the observed Friday 19:00Z boundary, with the percentage each would imply at $8.79/pp:

2026-08-14218$14.9455%1.7%

2026-09-18 (partial)2,098$398.9987%45.4% ← anchor

The week of 2026-08-28 lands at 137.8%, which cannot happen. Three explanations, and this spike cannot distinguish them:

  1. Limits were genuinely hit that week. Plausible — it is the heaviest week by far and the only one with substantial Fable usage ($277 fable-5 + $49 fable-5.1), which burns both the all-model weekly and its own scoped cap. A grep of the transcripts for limit-reached messages found no positive evidence, but that grep is weak evidence of absence.
  2. The ratio is not constant across weeks — plan limits, model list prices, or Anthropic's internal weighting changed within the six-week span.
  3. The percentage is not linear in list-price dollars — e.g. cache reads are weighted differently from the public 0.1× when charged against a subscription plan. Given cache reads swing between 55% and 87% of the dollar across these weeks, a different weight would reorder the table substantially.

All three point the same direction for the design: do not hardcode a constant.

9. Coverage: what the transcripts can never see

The ticket predicted "something exhaustive probably isn't possible". Correct — and the endpoint quantifies the gap for you.

SurfaceShare of current weekVisible in local transcripts?
Claude Code (incl. subagents, Claude Desktop's Claude Code)94%yes
Cowork6%no
Chats (claude.ai)0%no
Other0%no

Two pieces of corroborating evidence that the 6% is real and really invisible:

  • The weekly_scoped Fable cap reads 19% for the current window, yet there is zero Fable usage in the local transcripts in that window — the last local Fable request was 2026-09-10, two windows ago. Something off-machine used Fable this week; Cowork is the obvious candidate.
  • This is the general failure mode: usage on a second machine, on the web, or on a surface with no local log is structurally invisible. There is no fix, only disclosure.

So any feature built on this must present a Claude-Code-attributed figure and say so, using seven_day_breakdown to state the covered fraction rather than implying totality. When Claude Code's share drops, the estimate's authority drops with it — and the widget knows by how much.

10. Open questions a follow-up must resolve

Is the dollars→percent relationship linear within a week?
Untested. Resolvable in one week: log (capturedAt, seven_day.utilization, cumulative $ since window_started_at) on every poll the widget already makes (every 1–5 minutes) and check the fit. A straight line through the origin means the model holds; curvature or a step means it does not.
Is the constant stable across weeks?
Unknown, and the 08-28 row argues against it. Resolvable only by collecting several weeks of the log above. Nothing in the existing data can answer this — the endpoint returns only the current window and the app's SnapshotCache keeps only the last good reading (~/Library/Application Support/claude-usage-menu-bar/usage-backup.json, single object, overwritten each poll). No history exists anywhere on this machine.
Are cache reads weighted the same by plan accounting as by list price?
The highest-leverage sub-question, since cache reads are 55–87% of the dollar. Testable once several weeks of logged pairs exist: fit percentage against the four token classes separately and see whether the recovered cache-read coefficient matches 0.1× base input.
Do limit_dollars / used_dollars ever become non-null?
They are null on this plan today. If they ever populate, they are the ground truth and the whole calibration problem disappears. Cheap to watch for — one null check in the poller.
Does the app's inferred window start ever disagree with window_started_at?
They matched to the millisecond in this sample. Worth asserting rather than assuming, because an off-by-one-window start silently ruins every cost figure downstream.

11. Implementation shape, if this becomes a feature

Not a spec — a sketch of what the evidence above supports, for whoever refines CLU-3.

  1. A transcript scanner. Walk ~/.claude/projects/**/*.jsonl, keep type == "assistant" rows with a usage block and a known model, group by (message.id, requestId), take per-field max, price with the §5 table including the 5m/1h cache-write split and Fable 5.1's 0.025× cache read. Incremental by file mtime and byte offset; a full cold scan is under a second anyway.
  2. Read only usage. The transcripts contain full prompt and tool text. This repo's posture is that nothing sensitive reaches disk or logs. The scanner should parse and discard, never cache message content, and the aggregate it writes should contain numbers only — the same discipline SnapshotCache already applies.
  3. Decode the fields the endpoint already sends — seven_day_breakdown (for the window start and the coverage share) and the *_dollars nullables. Small, additive change to UsagePoller.UsageResponse, and independently useful.
  4. Log the calibration pairs. Append (capturedAt, utilization, claudeCodeShare, cumulativeCost, windowStartedAt) to a rolling on-disk log on each poll. This is the only way to answer the week-over-week question, and it costs one line per poll. Do this first — it starts accruing the data the rest depends on.
  5. Fit, don't hardcode. Derive $/pp from the current window's own logged pairs; show the implied weekly budget as a derived, clearly-provisional number. Fall back to "cost only, no percentage mapping" when the fit is poor or the window is young.
  6. Test against OTel. A fixture of transcript rows whose expected cost came from claude_code.cost.usage pins the pricing table and the dedup policy — the two things most likely to silently drift. Tests/ClaudeUsageCoreTests/ already has the shape for this.

12. Reproducing this

The analysis scripts were scratch, not committed. Each finding is reproducible from the description above; the load-bearing invocations were:

# Live usage snapshot (the token is read, used, and never printed)
T=$(security find-generic-password -s "Claude Code-credentials" -w \
    | python3 -c 'import sys,json;print(json.load(sys.stdin)["claudeAiOauth"]["accessToken"])')
curl -s -H "Authorization: Bearer $T" -H "anthropic-beta: oauth-2025-04-20" \
     https://api.anthropic.com/api/oauth/usage | python3 -m json.tool

# Claude Code's own cost metric for one request (the §5 oracle)
CLAUDE_CODE_ENABLE_TELEMETRY=1 OTEL_METRICS_EXPORTER=console \
OTEL_METRIC_EXPORT_INTERVAL=3000 OTEL_LOGS_EXPORTER=none \
  claude -p "reply with the single word: ok" --model haiku

# Independent cost cross-check
npx ccusage daily --since 20260918 --json

The cost computation itself is: group assistant rows by (message.id, requestId), per-field max over input_tokens, cache_creation.ephemeral_5m_input_tokens, cache_creation.ephemeral_1h_input_tokens, cache_read_input_tokens, output_tokens, server_tool_use.web_search_requests; multiply by the §5 table; filter to the window by row timestamp.

All figures measured on one machine on 2026-09-21 against a single Claude plan. The usage endpoint is undocumented and its response shape can change without notice — the same caveat the README already carries for the rest of this project. Prices are public list prices as of 2026-09-21 and will drift.
