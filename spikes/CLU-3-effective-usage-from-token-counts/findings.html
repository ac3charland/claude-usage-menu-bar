1. Verdict

Yes — an accurate, cheap, fully local measurement of API-equivalent spend is available, and it can be joined to the usage percentage this widget already polls. Claude Code writes a complete per-request usage block to its JSONL transcripts; multiplying those by public list prices reproduces Claude Code's own cost figure to the cent (verified exactly, §5). A full scan of 277 MB / 448 transcripts takes 0.73 s.

But the conversion factor — "how many dollars is one percentage point of my weekly plan?" — is not a constant you can look up or hardcode. The endpoint never exposes the denominator (limit_dollars is null on this plan). It has to be measured, per window, from paired observations of utilization and cost.

Those paired observations already exist. The widget's own log file has been recording weekly=NN% every two minutes since 2026-09-03 — 4,969 snapshots covering four weekly windows. Joined to the transcripts it yields a real dollars-per-percentage-point series (§8), not an extrapolation.

A tracking system is feasible, and §11 specifies it. The estimator that works uses tick crossings: when the reported integer utilization steps n → n+1, the true value crossed n+0.5 at that instant, so a week run to 98% yields ~98 sharp observations instead of one. Regressing cumulative cost on those gives the dollars per point, with an intercept that absorbs the endpoint's accounting lag.

Two constraints are non-negotiable and both were measured, not guessed. (1) The estimate only converges once a window passes ~70% utilization — measured at 50% it reads 46% high, at 10% it reads 322% high. A light week is not a data point. (2) The regression's own error bars lie: at a 20% cut-off it reports ±7% while being 182% wrong. Gate on utilization reached and compare only over matched spans. Respect both and the method is tight — two windows compared over an identical 0.5→47.5% span agreed to 0.4% ($7.96 vs $7.99).

On whether the allowance has already been cut: no evidence that it has. The only two windows comparable like-for-like are indistinguishable. An earlier apparent halving was an artifact of comparing a half-finished window against a complete one. See §8.

The one field that makes or breaks this is the per-surface breakdown. Each window gives one equation, local$ = k × pct × coverage, in two unknowns. The endpoint already returns coverage in seven_day_breakdown; the widget just doesn't log it. Without it a silent cut is indistinguishable from working outside Claude Code — and the 2026-09-11 window would have reported an 8× collapse that was really just a quiet week at the terminal.

Expected precision: ±5% on a full window, detecting week-over-week changes of about ±15–20%. Enough to catch a silent quarter-cut within two heavy weeks; not enough to resolve a 5% drift. Model mix is the confounder that dominates everything else.

The ticket's worry about Claude chat sessions is measurable and currently moot. The endpoint returns that same per-surface breakdown. Right now: Claude Code 94%, Cowork 6%, Chats 0%. See §9.

Rows with message.model == "<synthetic>" (39 in this corpus) are locally-generated placeholders — API error notices, interrupt markers. They carry a usage block but cost nothing. 4. The dedup trap — the single biggest correctness risk

Claude Code writes several rows per API response while streaming. Each has its own uuid but the same message.id and requestId, and the token fields grow across them. Forking or resuming a session copies history into a new file, so the same request can also appear under several sessionIds. In this corpus, 35,004 rows collapse to 20,204 real requests — 73% inflation if you just sum.

There are three candidate policies and only one is right. Measured over the whole corpus:

Token field naive sum first-wins per-field max ✓
input_tokens 107,492 +93% 55,65255,652
cache_creation_input_tokens 134,230,243 +121% 60,746,48360,746,483
cache_read_input_tokens 6,787,764,019 +62% 4,189,360,5974,189,360,597
output_tokens 18,298,440 +52% 5,768,891 −52% 12,055,611
The non-obvious half

First-wins dedup — the obvious fix, and what ccusage shipped for a while — silently loses 52% of output tokens. 7,317 of 20,204 request groups (36.2%) have a first row whose output_tokens is an intermediate streaming snapshot rather than the final count. The input and cache fields are identical across rows in a group; only output_tokens grows.

Correct policy: group by (message.id, requestId), take the per-field maximum. Fall back to a session-scoped key for the handful of rows with no requestId (7 rows here). This is the same conclusion ccusage reached after a 2× regression and a cross-session dedup fix.

On this machine the dollar impact of the output-token half is modest — output is 2–13% of the bill because cache reads dominate (§5) — but it is a 52% error on the one number a user would most expect to be right, and it costs nothing to avoid.

Cache reads are normally 0.1× base input. Fable 5.1 is the exception at 0.025× ($0.25/MTok, not $1.00) — a table that assumes a uniform 0.1× multiplier overcharges Fable 5.1 cache reads by 4×. Web search adds $10 per 1,000 searches on top (usage.server_tool_use.web_search_requests); web fetch is free.

The formula is provably right

Ran one request under Claude Code's own OpenTelemetry console exporter and compared its claude_code.cost.usage against the cost derived from the transcript row for the same request:

SourceUSDDetail
Claude Code, claude_code.cost.usage0.0206061 haiku-4-5, query_source: main
Derived from transcript usage × list price0.0206061 in 10, out 60, cacheRead 13,701, cacheWrite 1h 9,463
Difference0.0000000exact

Decomposing confirms it term by term: 10 × $1 + 60 × $5 + 13,701 × $0.10 + 9,463 × $2.00 per MTok. That last rate is the 1-hour cache-write price, which is only reachable by reading usage.cache_creation.ephemeral_1h_input_tokens rather than the flat cache_creation_input_tokens. Claude Code prices the 5m and 1h cache writes separately and so must we.

Independent cross-check: npx ccusage daily --since 20260918 reports $399.91 for the current weekly window against this spike's $398.99 — 0.2% apart, entirely explained by ccusage bucketing on local calendar days while the window starts at 19:00Z mid-day Friday.

Cache reads are the bill

Across the six weeks measured, cache reads are 55–87% of the list-price dollar — 87% in the current week. Output tokens are 2–13%. Any summary that leads with "tokens" without separating cache reads will mislead badly, and any modelling of how the plan weights usage has to get the cache-read term right first because everything else is noise next to it.

6. Hooks: the answer is no. OTel: the answer is yes.

The ticket asks whether Claude Code hooks can feed this. They cannot supply token or cost data. Checked every event in code.claude.com/docs/en/hooks:

EventTokens / cost?Carries transcript_path?Useful as a trigger?

So a hook can only ever say "something happened, here is where to look". The docs say as much: for billing/usage tracking they point at OpenTelemetry, correlated by prompt_id.

OpenTelemetry does carry it — verified live

With CLAUDE_CODE_ENABLE_TELEMETRY=1 and OTEL_METRICS_EXPORTER=console, Claude Code emits, after every API request:

  • claude_code.cost.usage — unit USD, a counter, attributed by model, query_source (main/subagent/auxiliary), session.id, and optionally effort, speed, agent.name, skill.name.
  • claude_code.token.usage — same attributes plus type ∈ {input, output, cacheRead, cacheCreation}.
  • Also claude_code.session.count, claude_code.active_time.total.
Why this spike does not recommend OTel as the data path
  • It is opt-in and prospective. Turning it on today tells you nothing about last week. The transcripts are already six weeks deep.
  • It requires the user to export env vars into every shell that launches claude, or set them globally — a real install burden for a menu-bar widget that today needs nothing but a Keychain read.
  • Collecting it means running a collector (otlp/prometheus) or scraping console output. console writes to the CLI's own stdout, which is not capturable from another process.
  • The metric payload includes user.email, user.account_id, organization.id — this repo's stated posture is that nothing sensitive is written to disk or logs. Routing it anywhere needs care.
  • It is not more accurate. §5 shows the transcript-derived figure equals claude_code.cost.usage exactly — because they compute it the same way.

OTel's real value here is as the oracle: it is Claude Code's own answer, so it is the right thing to validate a transcript-based implementation against in a test, exactly as done in §5. It is also the only source that attributes cost to skill.name / agent.name, which the transcripts do not — relevant only if per-skill attribution is ever wanted.

Is the weekly allowance shrinking? The direct measurement

This is the question the ticket actually exists to answer, and it needs independently measured pairs of (utilization, cost) — one per week. Extrapolating a single week's rate backwards cannot detect a change in that rate; it assumes the answer.

The history exists after all

The widget has been writing Snapshot: session=… weekly=NN.N% (elapsed …) to ~/Library/Application Support/claude-usage-menu-bar/claude-usage.log every two minutes since 2026-09-03 — 4,969 usable observations across four weekly windows, and the rotated .1.log extends it further back. The elapsed fraction recovers each window's start time, so every line can be joined to the transcript cost accumulated since that start. No new instrumentation was needed to get this far; it was a side effect of ordinary logging.

The table above compares windows at different stages of completion, and that turns out to invalidate the comparison. The estimate is strongly biased by how far through a window you measure it — see §11, where refitting the one full-span window at successive cut-offs gives $22.09/pp at 10% utilization, $7.65 at 50%, and $5.23 at 98%. A window observed half-way through reports roughly 50% high.

Result

$7.96 vs $7.99 — the two comparable windows are indistinguishable. The apparent devaluation in the previous table was an artifact of comparing a half-finished window against a complete one. On the evidence available there is no sign that the weekly allowance changed between 2026-09-04 and now.

  • 2026-09-11 remains the warning. $0.95/pp — an apparent 8× collapse in plan generosity that is really just $50 of local spend against a week largely spent elsewhere. Without the coverage figure this window would have been read as a catastrophic silent cut. It is the single strongest argument for logging seven_day_breakdown.
  • 2026-08-28 cannot be judged. The log begins mid-window at 44%, so there is no overlap with the low-utilization span the others share. Its ≥$16.57 bound is also the Fable-heavy one (27% of its dollars at 2× Opus list price). Unusable either way.
Why this cannot be settled yet

Each window yields one equation in two unknowns:

local_dollars  =  k_w  ×  utilization  ×  coverage_w

— where k_w is the rate we want and coverage_w is Claude Code's share of that week. Four windows, four equations, eight unknowns. A shrinking k and a falling coverage are the same observation. The fix is not more cleverness, it is one more logged field: seven_day_breakdown.rows pins coverage_w and collapses the system to one unknown per week.

Three confounders any future comparison has to control

  1. Coverage — as above. Fixed by logging the breakdown.
  2. Model mix. Comparing a Fable-heavy week to an Opus-only week compares list-price ratios, not plan generosity. Either compare like-for-like weeks, or accumulate enough windows to fit per-model coefficients. The separate weekly_scoped Fable cap is a hint that the plan does not treat models interchangeably.
  3. List prices move. A cut to Opus's public price would drop $/pp with no change whatsoever to the allowance — the metric would report a devaluation that did not happen. Denominate the series in a frozen price table (snapshot the rates, version them, keep using the old one for the historical series) so the unit stays fixed. This matters: Sonnet 5's price changed within the period these transcripts cover.
Windows that max out read low

Spend past 100% is billed to extra-usage credits and does not advance the percentage, so a window that hits the cap accumulates local dollars against a frozen denominator and reports an inflated $/pp. None of the four windows above reached 100% (peak 98%), so none is affected here — but the estimator must exclude maxed-out windows, and extra_usage.used_credits is the flag for detecting them.

9. Coverage: what the transcripts can never see

The ticket predicted "something exhaustive probably isn't possible". Correct — and the endpoint quantifies the gap for you.

Claude Code (incl. subagents, Claude Desktop's Claude Code)94%yes
Cowork6%no
Chats (claude.ai)0%no

Two pieces of corroborating evidence that the 6% is real and really invisible:

  • The weekly_scoped Fable cap reads 19% for the current window, yet there is zero Fable usage in the local transcripts in that window — the last local Fable request was 2026-09-10, two windows ago. Something off-machine used Fable this week; Cowork is the obvious candidate.
  • This is the general failure mode: usage on a second machine, on the web, or on a surface with no local log is structurally invisible. There is no fix, only disclosure.

So any feature built on this must present a Claude-Code-attributed figure and say so, using seven_day_breakdown to state the covered fraction rather than implying totality. When Claude Code's share drops, the estimate's authority drops with it — and the widget knows by how much.

10. Open questions a follow-up must resolve

Is the dollars→percent relationship linear within a week?
Untested. Resolvable in one week: log (capturedAt, seven_day.utilization, cumulative $ since window_started_at) on every poll the widget already makes (every 1–5 minutes) and check the fit. A straight line through the origin means the model holds; curvature or a step means it does not.
Is the rate stable across weeks — i.e. is the allowance being quietly cut?
The central question, and §8 gets partway: four windows recovered from the widget's log, three consistent at $7–9/pp and one (2026-08-28) implying ≥$16.57/pp. Not settled, because that window is also the Fable-heavy one. Settling it needs the per-surface breakdown logged alongside the percentage — without coverage_w the system is underdetermined. Note the endpoint returns only the current window and SnapshotCache (usage-backup.json) keeps only the last reading, so the log file is the sole historical record and it starts 2026-09-03. It is also rotated and will eventually be lost: the calibration series deserves its own append-only file, not a side effect of a rotating log.
Are cache reads weighted the same by plan accounting as by list price?
The highest-leverage sub-question, since cache reads are 55–87% of the dollar. Testable once several weeks of logged pairs exist: fit percentage against the four token classes separately and see whether the recovered cache-read coefficient matches 0.1× base input.
Do limit_dollars / used_dollars ever become non-null?
They are null on this plan today. If they ever populate, they are the ground truth and the whole calibration problem disappears. Cheap to watch for — one null check in the poller.
Does the app's inferred window start ever disagree with window_started_at?
They matched to the millisecond in this sample. Worth asserting rather than assuming, because an off-by-one-window start silently ruins every cost figure downstream.

11. The system going forward

This is the part that matters: a design that records, week after week, "what dollar value of weekly usage is my cap, and is it different this week from last week?" — and an honest account of how precisely it can answer.

The estimator: tick crossings, not end-of-week readings

The endpoint reports utilization as an integer. That looks like a precision ceiling but is actually an opportunity: when the reported value steps from n to n+1, the true utilization crossed n+0.5 at that instant. Each tick is therefore a sharp observation, and a week that runs to 98% yields ~98 of them rather than one.

for each tick (reported n → n+1 between polls at t₀, t₁):
    x = n + 0.5                                   # true utilization at the crossing
    y = Σ cost(requests in [window_start, t₁])    # cumulative local spend

fit  y = slope·x + intercept
     slope     → dollars per percentage point, ×coverage
     intercept → absorbs the endpoint's accounting lag (a roughly constant offset)

dollars_per_point = slope / claude_code_share
weekly_cap_value  = dollars_per_point × 100

Fitted on the four recoverable windows this yields a slope with a 4.5–13% standard error, and the intercept does real work — it ranged from −$99 to +$1,140 across windows, i.e. the lag is large and ignoring it would bias the slope badly.

Two hard constraints fall out of this
  1. The estimate only converges past ~70% utilization. Below that it is biased high, severely so early on. A week you only drive to 30% yields no usable measurement of the cap — you simply do not learn the denominator until you approach it.
  2. The regression's own error bars are dangerously overconfident. At the 20% cut-off it reports ±7% while being 182% wrong. The residual scatter is not the error; the span is. Never surface the reported σ as the confidence. Gate on utilization reached, and compare only over matched spans.

Once both constraints are respected the method is solid: the like-for-like comparison in §8 (two windows, identical 0.5→47.5% span) agreed to 0.4% — $7.96 vs $7.99.

So: what can it actually detect, and how fast?

QuestionAnswer
First usable cap estimate End of the first window that reaches ~70%+ utilization. If you routinely run the plan hot, that is one week; if not, whenever it next happens.
First week-over-week comparison Two such windows — so ~2 weeks of heavy use, longer if light weeks intervene. Light weeks are not data points.
Precision on a full-span window ~±5% (1σ) from the fit, plus the coverage figure's own integer rounding (~±0.5%).
Smallest detectable week-over-week change Roughly ±15–20% at 2σ on a matched pair of full windows. Enough to catch a silent quarter-cut quickly; not enough to resolve a 5% drift.
Confounder that dominates everything else Model mix (§8). A Fable-heavy week is not comparable to an Opus week at all.

What to record, on every poll

One append-only line per poll, numbers only. The widget already polls every 1–5 minutes, so this is nearly free:

{
  "capturedAt":        "2026-09-21T17:34:17Z",
  "windowStartedAt":   "2026-09-18T19:00:00Z",   // seven_day_breakdown, not inferred
  "weeklyPct":         48,
  "sessionPct":        8,
  "surfaceShares":     { "claude_code": 94, "cowork": 6, "chat": 0, "other": 0 },
  "scopedPct":         { "Fable": 19 },
  "costSinceWindowStart": 396.47,
  "costByModel":       { "claude-opus-5": 396.00, "claude-haiku-4-5": 0.39 },
  "tokensByClass":     { "input": …, "cacheWrite5m": …, "cacheWrite1h": …,
                         "cacheRead": …, "output": … },
  "extraUsageCredits": 442,                      // minor units - flags maxed-out windows
  "priceTableVersion": "2026-09-21"
}

Five fields are load-bearing and each is easy to leave out:

FieldWhy the system breaks without it
surfaceShares The one that makes it work at all. Without it the system is underdetermined and the 2026-09-11 window reports an 8× silent cut that never happened.
priceTableVersion A public price cut would drop $/pp with no change to the allowance — a devaluation that did not occur. Freeze the rates, version them, keep using the old table for the historical series. Sonnet 5's price already changed inside the period these transcripts cover.
costByModel Lets a later analysis control for, or fit, per-model weighting — the dominant confounder.
tokensByClass Cache reads are 55–87% of the dollar. Keeping the classes separate is what makes it possible to later test whether the plan weights them the way list price does.
extraUsageCredits Flags a window that maxed out, whose $/pp is inflated and must be excluded.
Do not rely on claude-usage.log

It carries the history today by accident, and §8 only exists because of that. But it rotates (claude-usage.1.log is already the overflow) and will silently lose the series. The calibration log needs its own append-only file with no rotation, or rotation that preserves it.

Pieces, and where they go in this repo

  1. TranscriptScanner (new, ClaudeUsageCore) — walks ~/.claude/projects/**/*.jsonl, keeps type == "assistant" rows with a usage block and a known model, groups by (message.id, requestId), takes the per-field max (§4), prices with the frozen table including the 5m/1h cache-write split and Fable 5.1's 0.025× cache read (§5). Incremental by file mtime + byte offset; a full cold scan is 0.73 s anyway.
  2. UsageResponse additions — decode seven_day_breakdown (window start + surface shares) and the limit_dollars/used_dollars nullables. Small and additive; useful on its own even if nothing else ships. If those dollar fields ever go non-null, they are ground truth and the entire estimator becomes unnecessary — worth a check that says so loudly.
  3. CalibrationLog (new) — appends the record above on each poll, alongside the existing SnapshotCache write in UsageEngine.
  4. CapEstimator (new) — tick extraction, the two-parameter fit, the utilization gate, matched-span comparison against prior windows.
  5. Surfacing — a line in the popover, e.g. "This week's cap ≈ $850 of API usage · last week $846 · no change", and explicitly "not enough of the window used yet" until the gate passes. Given the bias table above, showing a number early would be worse than showing nothing.
  6. Tests — a fixture of transcript rows whose expected cost came from claude_code.cost.usage (§5) pins the price table and the dedup policy, the two things most likely to drift silently. Tests/ClaudeUsageCoreTests/ already has the shape.

Privacy

Transcripts contain full prompt and tool text. This repo's stated posture is that nothing sensitive reaches disk or logs, and SnapshotCache already scrubs on write. The scanner must parse and discard — never cache message content — and every field in the calibration record above is a number, a model ID, or a timestamp by construction. Keep it that way.

Current best answer

The weekly cap is worth roughly $800–$850 of API-list-price usage — from the matched-span fit ($7.99/pp ÷ 0.94 coverage ≈ $8.50/pp × 100), with the current window only 48% through and therefore biased high; the fuller 2026-09-04 window puts it nearer $5.23 ÷ coverage. Call it $550–$850, not yet pinned. The honest statement is that one full-span window plus its coverage figure would collapse that range to about ±5%, and nothing in the data so far suggests the number has moved between the two comparable windows.

# 2026-09-03T06:35:20Z INFO Snapshot: session=24.0% (elapsed 68.4% ·on-pace)  \
#   weekly=44.0% (elapsed 78.3% ·on-pace)  fable=37.0% (elapsed 78.3% ·on-pace)

To rebuild §8: parse each Snapshot: line for its timestamp, weekly= percentage and weekly elapsed fraction; recover the window start as timestamp − elapsed × 7d (snap to the hour to absorb the 0.1% logging resolution, and merge starts within ~2h of each other); take the highest percentage observed per window; sum the transcript cost from that window's start to that observation's timestamp; divide.

Two estimators were tried and one is wrong. The cumulative form above works because both quantities share an origin. A marginal form — regressing Δcost against Δpercent between consecutive polls — does not: with integer percentages and a 2-minute poll, a single point ticks over as soon as it rounds up, so the cost measured in that interval is an arbitrary fraction of the cost actually behind it. It produced estimates 3–10× too low and should not be revived.

The cost computation itself is: group assistant rows by (message.id, requestId), per-field max over input_tokens, cache_creation.ephemeral_5m_input_tokens, cache_creation.ephemeral_1h_input_tokens, cache_read_input_tokens, output_tokens, server_tool_use.web_search_requests; multiply by the §5 table; filter to the window by row timestamp.

All figures measured on one machine on 2026-09-21 against a single Claude plan. The usage endpoint is undocumented and its response shape can change without notice — the same caveat the README already carries for the rest of this project. Prices are public list prices as of 2026-09-21 and will drift.
