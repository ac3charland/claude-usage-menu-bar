Spec · CLU-4

Weekly usage budget, compared to last week

Add one line under the Weekly bar that says whether the weekly limit is worth about the same in API dollars as last week, or noticeably more or less. In other words: is the subsidy changing? Show it only when the data supports the claim.

1. What ships

A single footnote line under the Weekly row of the popover. It compares this week's usage budget with last week's. The usage budget is the subsidy: the dollar value, at public API list prices in effect when the usage happened, of the Claude Code usage that one percentage point of the weekly limit covers. The comparison uses the same range of utilization in both weeks. It reads one of the following, or nothing:

  • Usage budget similar to last week
  • Usage budget down 25% from last week or up 20%: a clear change of 20% or more
  • Usage budget down ~15% from last week: a smaller change, or any change read early in the week, marked with “~”

The line favors being visible over being certain. It appears once both weeks have passed 30%, the reading has stopped moving as the span grows, and Claude Code accounts for at least a quarter of each week's usage. When something could explain the number, such as a price change, a new model mix, or usage outside Claude Code, the tooltip says so rather than hiding the line. The other gates in §5 only catch missing or broken data. The math was put through an adversarial review; §13 lists what changed. Readings are also recorded when they are not shown, so the thresholds can be tuned from evidence (§6.4).

The work follows the tracking system that CLU-3 §11 designed. It adds a transcript scanner, a per-poll calibration log, and a tick-crossing estimator, and then shows the estimator's matched-span comparison in the panel. It also adds something the spike did not have: a dated price history fetched from Anthropic's pricing page, so each request is priced at the rate in effect when it was made (§6.2). The feature does not show an absolute dollar figure for the limit (see §10).

2. Decisions

QuestionDecisionWhy
What does the budget measure? The subsidy: API dollars at the prices in effect when the usage happened, per percentage point of the weekly limit (ticket owner, in refinement) The question is “how much subsidized usage am I getting, and is that changing?” Tokens are not a stable unit of work, because newer models do more per token, so a fixed-price “amount of work” measure answers a different question. This deliberately overrides CLU-3's advice to freeze the price table. Example: Opus's list price drops 20%, and the dollar amount the plan allows drops 20% too. In usable work that's roughly a wash, but the subsidy fell 20%, and that's worth knowing. So the line says “down 20%”, and the tooltip explains that with the same prices in both weeks it would read “similar” (§3). A frozen table would say “similar” and hide the drop.
Where do prices come from? Anthropic's pricing page, fetched as markdown once a day, kept as a dated history, with a built-in table as the fallback (ticket owner, in refinement) A new model or a price change is picked up without a code change. The page is published by Anthropic, the only company the app already talks to. LiteLLM's JSON was considered: it is easier to parse, but it would add a download from GitHub, a third party. The Models API has no price fields.
When is the line allowed to appear? Matched span, both weeks ≥ 30%. Below 50% the reading is marked “~” as an early read (ticket owner, in refinement; first set at 50%, then lowered for visibility) A span gate alone isn't enough. Review showed that a week's work can be spread so unevenly that early readings swing by more than 50% (§5 replay), so a stability check (G13) now decides when an early reading appears. The 30% gate stays as the earliest possible point, and readings under 50% are marked “~”. Shadow readings (§6.4) measure how far readings still move. The 70% gate from the spike is for an absolute estimate, which this feature does not show.
How is the rate measured? A block-mean span rate against Claude Code points, not an OLS slope divided by one share (adversarial review) The OLS slope on cumulative data weights the middle of the span most and the ends not at all, so it doesn't measure “the first S%”. One cumulative share is the wrong divisor once the span starts above 0 or the share drifts. See §4.4.
Backfill past weeks from claude-usage.log? No. Start recording fresh (chosen by the ticket owner) The log never recorded Claude Code's share of usage, so backfilled weeks would have to assume 100%, which misreads quiet weeks like 2026-09-11. The log also rotates; it now reaches back only to 2026-09-12.
Where does a week start? At the weekly reset time from the OAuth usage endpoint: seven_day.resets_at − 7 days (ticket owner, in refinement) This is the same source the app already uses for the Weekly row's reset countdown and pace mark (UsageSnapshot.compute), so the comparison's week always matches the week on screen. seven_day_breakdown.window_started_at is used only as a cross-check (§6.6).
What is “last week”? The window that reset into the current one: its reset time equals the current start, within 1 hour. If the weeks are not back to back (for example, a week with no usage at all), there is no honest “last week”, so nothing is shown. The line never falls back to an older week.
Show direction both ways? Yes: down, up, and same. The ticket gives “down” as an example. An increase is equally meaningful and uses the same math.
How to express “significant confidence”? Graded wording, not a dead band: within about ±10% reads “similar”, under 20% reads “~N%” without emphasis, and 20% or more reads “N%”, emphasized when down (ticket owner, in refinement) Hiding the 10–20% band would hide exactly the size of a quiet cut worth knowing about. The random error of a reading is a few percent. The error that matters is systematic: how the week's work (cache-read share, model, and off-Mac usage) is spread across the span. How large that is across ordinary weeks isn't known yet, and it is what the shadow readings measure. Emphasis is kept for readings that are not approximate.
Model mix and usage outside Claude Code Explain in the tooltip rather than hide, unless Claude Code is under a quarter of a week's usage (ticket owner, in refinement) A model switch would otherwise hide the line for about two weeks, and one is happening now (Opus 5 → Opus 5.5). Under the subsidy framing a switch really does change the subsidy received, so it is shown and flagged. The Claude Code floor was lowered to 25% because the owner runs many sessions outside the terminal. Below that, as in the week of 2026-09-11 (about 12%), there is too little local usage to measure, so the line still hides. At low shares, the Claude Code points floor in G6 and the stability check (G13) are what protect the reading.
Wording of the “similar” line Usage budget similar to last week rather than the ticket's “About the same usage as last week”. The ticket's phrase could be read as “you used about the same amount”, which is a different claim. Making all three lines start with “Usage budget …” keeps them parallel and unambiguous. “About the same as” was tried first and measured 0.4pt too wide for the panel (§3).

  • r is k_this / k_last, where k is local API dollars per Claude Code percentage point of the weekly limit, at the prices of the time (§4). “Down” means one percentage point now covers fewer API dollars, so the subsidy shrank.
  • The reading is derived from r in one place, so the “~” and the number can never disagree: 
    reading(r):
    if |ln r| < ln 1.10            → similar       // symmetric: swapping the weeks never changes the band
    direction = r < 1 ? down : up
    N = max(10, 5 · ⌊|r − 1| · 100 / 5 + 0.5⌋)     // nearest 5, halves round up, never below 10
approximate = N < 20 or earlyRead               // shows “~”
emphasized  = direction == down and not approximate
    A 23% drop reads “down 25%”; a 12% drop reads “down ~10%”. Rounding to 5 avoids suggesting more precision than the method has.
  • The arrows are straight (vertical), not the diagonal arrow the pace footnote uses, so “budget up” is never confused with “ahead of pace”.
  • The line has a hover tooltip (.help) that states what it measures: API-price value of the Claude Code usage each 1% of your weekly limit covered, at the prices of the time, this week vs. last week, from L% to S% of each week. L and S are the ends of the matched span. When L is under 1%, the tooltip says “over the first S% of each week” instead.
  • Tooltip notes. After the first sentence, the tooltip adds any of these that apply, in this order (conditions in §4.4):
    1. Early read (span under 50%): Early read: based on the first S% of each week, so it may still move.
    2. Prices changed (a price used in either week changed since last week began, and pricing both weeks the same way gives a different reading): API prices changed since last week. With the same prices in both weeks this would read “similar”. When that reading is “similar”, add In usable work, that's roughly a wash. This separates a subsidy change caused by a price move from one caused by the plan.
    3. Model mix changed: Your model mix changed: last week was mostly Opus 5, this week mostly Opus 5.5. That alone can move this number. The “mostly” clause appears only when the top model differs.
    4. Cache-read share changed: Cache reads were 87% of this week's local dollars and 63% of last week's. The plan may not count them at list price, and that alone can move this number. See §11 for why this matters.
    5. Usage outside Claude Code (Claude Code under 90% of either week): Claude Code was 72% of this week's usage and 94% of last week's. Only sessions on this Mac are measured; the rest is assumed to count against the limit the same way.
  • Width. The line must fit on one line in 248pt of content width (280 minus 16 on each side). Measured at 11.5pt SF with NSAttributedString, including the 10pt glyph and 4pt spacing: “Usage budget similar to last week” is 198pt, “Usage budget down ~15% from last week” 240pt, “Usage budget down 85% from last week” (medium) 240pt, and “Usage budget up ~105% from last week” 232pt. The earlier wording, “about the same as last week”, measured 248.4pt and would have been cut off. Confirm with --render-popover.

4. How the comparison is computed

This builds on the CLU-3 §11 tick-crossing idea, with three changes, two of them from the adversarial review (§13). The rate is a block-mean span rate against Claude Code points instead of an OLS slope (§4.4). Dollars are rebuilt from each record's token counts when the comparison runs, at the prices in effect at each record's time (§4.2). Ticks are interpolated across gaps between polls (§4.3).

4.1 Window identity

  • windowStart = seven_day.resets_at − 7d, rounded to the nearest minute. The endpoint's resets_at jitters by fractions of a second between fields and polls (for example 18:59:59.720162 and 18:59:59.719877 in the existing test fixtures). The rounded value is the window key.
  • When seven_day.resets_at is null, the window is empty or fresh: no record is written and no comparison is shown.
  • The previous window is the recorded window whose windowStart + 7d is within 1 hour of the current windowStart.

4.2 Cost at the prices of the time

Records store cumulative token counts per model since the window started (§6.4). When the comparison runs, cost is rebuilt from the token increments between consecutive records, and each increment is priced with the history entry in effect at that record's time:

Δtok_j[m] = max(0, tokens_j[m] − tokens_{j−1}[m])     // consecutive records from one writer, same window; tokens_{−1} = 0
c_i       = Σ_{j ≤ i} Σ_m price(Δtok_j[m], PriceHistory.rates(m, at: capturedAt_j))
price(t, p) = t.input·p.in + t.cw5m·p.cw5m + t.cw1h·p.cw1h + t.cacheRead·p.read + t.output·p.out   (per MTok)
            + t.webSearch · $0.01                     // standard-speed keys only; "/fast" keys are excluded (G8)
  • Records are at most 30 minutes apart, which is finer than the price history's own daily resolution, so this is still time-of-use pricing.
  • Because cost is rebuilt on every evaluation, a model the daily fetch prices later, or a price change detected late, is corrected in every record at once. No step appears in c, and a week does not stay hidden after the fix arrives. The scanner's per-record cost field is informational (logs and debugging) and is not used here.
  • The same sum with the latest rates for every increment gives the equal-price cost c′, which is used only for the price note. The same sum over non-cache-read token classes gives cnr, which is recorded in shadow readings (§6.4).
  • Every record carries a writer. Deltas between two interleaved writers would double-count, so each window is evaluated from one writer's series: the app's, or else the writer with the most records.

4.3 Ticks

The records of one window, sorted by capturedAt, are r₀…rₙ. Each has integer utilization uᵢ = round(weeklyPct), Claude Code share sᵢ = surfaceShares.claude_code / 100, and cost cᵢ from §4.2. Track the running maximum M. Whenever uᵢ > M, each crossed half-point becomes one tick:

s = uᵢ − M                                  // points crossed between rᵢ₋₁ and rᵢ
for j in 1...s:
    x   = M + j − 0.5                       // true utilization crossed this value
    y   = cᵢ₋₁ + (j − 0.5)/s · (cᵢ − cᵢ₋₁)  // cost interpolated across the gap
    xcc = x · sᵢ                            // Claude Code percentage points at the crossing
    gap = s > 2                             // inferred across a long gap
M = uᵢ

For the usual single-point step this puts y at the midpoint of the two polls, which is at most half of one poll's spend from the spike's convention of using cᵢ. Interpolation matters when the Mac slept or the app was quit while usage moved several points. Gap ticks lie on the straight line between two polls by construction, so they carry no information of their own. They are kept, but they do not count toward G4. Removing any 6 hours of polls from the week of 2026-09-18 changed its rate by at most 1.6%. A decrease in utilization inside a window emits nothing, and M keeps its value; none occurred in 3,729 polls.

4.4 Matched span and span rate

lo = max(firstTick_this, firstTick_last)          // first crossing both weeks observed
hi = min(lastTick_this,  lastTick_last)           // last crossing both weeks reached
for each week w, with ticks restricted to lo ≤ x ≤ hi:
    head_w = ticks with x ≤ lo + 4                // 5 ticks
    tail_w = ticks with x ≥ hi − 4                // 5 ticks
    k_w    = (mean(tail_w.y) − mean(head_w.y)) / (mean(tail_w.xcc) − mean(head_w.xcc))
                                                  // local $ per Claude Code point, across the span
r      = k_this / k_last                          // the headline; Δ = r − 1
stable = | r(lo, hi) − r(lo, hi − 10) | ≤ 0.10    // same computation with the span cut 10 points short (G13)
  • Why not an OLS slope. For evenly spaced cumulative data, the OLS slope is a weighted average of the per-point increments, with parabolic weights: zero at the ends and 1.5× uniform in the middle. It does not measure “the first S%”, and its weights shift every time hi grows. In the week of 2026-09-18 it gave $8.94/pp at 79.5% against a true span average of $6.50/pp, because the expensive 30–50% stretch sat mid-span. The block-mean rate is exactly the span average the tooltip describes. Averaging 5 ticks at each end damps timing error at the endpoints. Its standard error is not computed and must never be shown (CLU-3 §11).
  • Why Claude Code points. Dividing by one cumulative share is wrong once the span starts above 0 (G2 is gone) or the share drifts inside the span. For example, with a 50% share at lo = 40 and 70% at hi = 70, the span's own share is (70·0.70 − 40·0.50) / 30 = 0.97, and dividing by 0.70 overstates k by 38%. Measuring against xcc uses the share at each end, so drift is accounted for. Comparing k across weeks still assumes other surfaces count against the limit the same way per point, the same assumption as before.
  • Where the error comes from. Random error is a few percent: the local spend in the two minutes before a tick had a median of $0.12 and a 90th percentile of $4 in the week of 2026-09-18. The error that matters is systematic: how the week's work is spread across the span. In that week, local cost per point by 10-point band was $0, 0, 7.9, 11.8, 19.2, 4.6, 0.4, and 2.0, and the span rate from 0.5 moved from $2.36 (at 29.5%) to $8.64 (49.5%) to $6.50 (79.5%). The spike's cut-off table (§11) shows the same effect with the opposite sign in a different week, so this is a property of the week, not a bias that can be corrected. Matching spans cancels it only when both weeks have a similar profile. The stability check (G13) is what keeps a still-moving reading off the screen.
// tooltip notes only (§3); they never change the headline
earlyRead = hi < 49.5
priceNote = a price used in either week changed since last week began
            and reading(r′) ≠ reading(r)              // r′ from c′ (§4.2)
mixNote   = TVD(cost share by model ID over the span, this vs last) > 0.20
readNote  = | readShare_this − readShare_last | > 0.10  // cache-read $ / local $ over the span
covNote   = min(s at hi this week, s at hi last week) < 0.90

5. Gates

Only the gates marked Hides suppress the line. G3, G6, and G13 are the confidence gates; the others catch missing or broken data. G2, G9, and G11 were loosened in refinement; G10 was redefined and G13 added after the adversarial review (§13). Retired gates stay in the table, marked, so the history is traceable and the numbering used elsewhere holds. Thresholds are named constants in one place (CapEstimator.Config) so they can be tuned from shadow readings (§6.4).

6. Components and file changes

6.1 UsagePoller.swift: decode the breakdown

Add an optional sevenDayBreakdown: SevenDayBreakdown? to UsageResponse (key seven_day_breakdown) with windowStartedAt: Date? and rows: [Row], where Row has key, displayName, and percent: Double. All fields are optional, and a missing object decodes to nil, so the existing test payloads, which have no breakdown, still decode. Add a surfaceShares: [String: Double] convenience keyed by row.key. The CLU-3 sample response is the fixture. No other fields are decoded (§10).

Check during implementation: capture one live seven_day_breakdown from a week that included Claude Code on the web. Local transcripts only cover the cli, sdk-cli, claude-vscode, and claude-desktop entry points; web sessions run in the cloud and leave nothing on this Mac. If the breakdown gives web sessions their own row, subtract it and use the local-only share as cov. If web sessions are folded into claude_code, keep the formula but record that finding in this spec, because cov then overstates what is local (§11).

6.2 PriceHistory.swift and PricingFetcher.swift (new, Core)

This is a dated history of list-price tables. It answers “what did model m cost at time t?” It is kept current by fetching Anthropic's pricing page, and it falls back to a built-in table.

Source

  • GET https://platform.claude.com/docs/en/about-claude/pricing.md. Anthropic serves its docs pages as markdown at a .md URL, about 47 KB. The request is a plain GET with no Authorization header, so the OAuth token never goes to the docs site. The timeout is 10 s.
  • The engine tries at most once every 24 hours, as an extra step after a successful usage poll, never on its own timer. After a failure it retries on the next poll that is at least 1 hour later.
  • Considered and rejected: LiteLLM's model_prices_and_context_window.json, the source ccusage uses. It is keyed by exact model ID and matched Anthropic's numbers for all six models on 2026-09-24. But it is a 2.9 MB download from GitHub, which would break the README's “no third-party servers” promise. The Models API (/v1/models) has no price fields and needs an API key the app does not have.

Parsing

  • Locate the model table by its exact header row: Model | Base input tokens | 5m cache writes | 1h cache writes | Cache hits and refreshes | Output tokens. Parse rows until the table ends.
  • In each model cell, strip markdown links, parentheticals such as (retired, …) and (limited availability), and <sup>…</sup> footnote markers. Then derive the ID from the name: lowercase it and turn spaces and dots into hyphens, so “Claude Opus 5.5” becomes claude-opus-5-5. Each price cell must match $<decimal> / MTok once footnote markers are removed.
  • Validation. The fetch is rejected as a whole if any check fails: the header matches; at least 5 rows parse; no more than half of the models already in the history are missing, since a larger loss points to a parse problem; and each row has cache read < input < 5m write < 1h write and input < output. On rejection, keep the last good table and log the reason once per day.
  • A model that disappears from the page, for example after retirement, keeps its last known rates. Models are never dropped from the history.
  • Prose footnotes, such as the note that Sonnet 5's scheduled 2026-09-01 increase was cancelled, are not parsed. A change counts once it appears in the table.

History and lookup

  • Stored in ~/Library/Application Support/claude-usage-menu-bar/pricing/: history.jsonl gets one line per distinct table, {"effectiveFrom", "fetchedAt", "source", "rates": {id: {name, in, cw5m, cw1h, read, out}}}, appended only when the rates differ from the latest entry. state.json holds lastAttemptAt and lastSuccessAt, which gate G12.
  • effectiveFrom is the fetch time at which a change was first seen. That is up to 24 hours after the real change, plus however long the page takes to update. The built-in table below is the implicit first entry, with effectiveFrom in the distant past.
  • rates(model, at: t): normalize the ID by stripping a trailing -YYYYMMDD. Transcripts record Haiku as claude-haiku-4-5-20251001, which the spike's table did not match. Then return the model's rates from the entry in effect at t. If the model is missing from that entry, use the earliest later entry that has it, so a new model's launch price applies back to its first use. If no entry has it, return nil, never a guess.
  • priceChanged(models, since: t) reports whether any of those models' rates differ between the entry in effect at t and the latest entry. It drives the tooltip attribution in §3.

6.3 TranscriptScanner.swift (new, Core)

Produces WindowUsage for all requests with windowStart ≤ timestamp ≤ capturedAt. For each model key it holds the totals of input, cacheWrite5m, cacheWrite1h, cacheRead, output, webSearch, and requests. It also holds cost, where each request is priced by PriceHistory.rates(model, at: request.timestamp) (§4.2), and unpriced, the number of requests that got no rate. This cost is informational only. The estimator rebuilds cost from the token counts (§4.2).

  • Root: $CLAUDE_CONFIG_DIR/projects if set, otherwise ~/.claude/projects. Enumerate *.jsonl recursively, because subagent transcripts live at <session>/subagents/agent-*.jsonl. Skip files whose mtime is earlier than windowStart.
  • Rows: type == "assistant" with a message.usage block. Use a cheap substring prefilter before JSON decoding, and cover it with a test so it never rejects a valid row. Decode with a minimal Decodable that declares only timestamp, requestId, sessionId, message.id, message.model, and the usage numbers (input_tokens, cache_creation_input_tokens, cache_creation.ephemeral_5m_input_tokens, cache_creation.ephemeral_1h_input_tokens, cache_read_input_tokens, output_tokens, server_tool_use.web_search_requests, speed). Content fields are never modeled.
  • Dedup (CLU-3 §4): group by message.id + requestId, falling back to sessionId + message.id when requestId is missing. Merge with the per-field maximum, never first-wins. A group's timestamp is the earliest row timestamp. The same request copied into a forked or resumed session collapses to one.
  • Cache-write split: use cache_creation.ephemeral_{5m,1h} when present. Otherwise treat the flat cache_creation_input_tokens as 5m.
  • Model key: the model ID as written. Rows with speed == "fast" go under "<model>/fast", so G8 can measure them and the cost function can exclude them.
  • Incremental: keep per-file state (inode, byte offset). Read from the offset to the last complete newline and keep any trailing partial line for the next scan. A shrunk or replaced file is re-read from 0; the dedup map makes that idempotent. Keep the per-request map for the current window only, and reset it when the window key changes.
  • Isolation: it runs off the main actor (an actor, or a serial queue behind a continuation). A missing or unreadable root returns nil and logs one warning. It never throws into the poll path.

6.4 CalibrationLog.swift (new, Core)

This is the append-only history CLU-3 asked for, so the series does not depend on the rotating claude-usage.log.

  • Layout: one JSON Lines file per window, ~/Library/Application Support/claude-usage-menu-bar/calibration/<windowStart>.jsonl, with the name formatted like 2026-09-25T1900Z.jsonl (no colons). Finding last week means opening one small file. Files are never rotated or pruned.
  • Record (v1): 
    {"v":1,
 "capturedAt":"2026-10-03T17:34:17Z",
 "writer":"app",                                  // "app" or "daemon"; see §4.2
 "windowStart":"2026-10-02T19:00:00Z",          // resets_at − 7d, minute-rounded
 "weeklyPct":48,
 "surfaceShares":{"claude_code":94,"cowork":6,"chat":0,"other":0},   // null if absent
 "scopedPct":{"Fable":19},                       // from snapshot.weeklyModels; for later analysis
 "usage":{"claude-opus-5-5":{"input":55652,"cacheWrite5m":0,"cacheWrite1h":60746483,
                             "cacheRead":4189360597,"output":12055611,"webSearch":0,"requests":2074,
                             "cost":1398.52,        // informational; the estimator reprices from tokens (§4.2)
                             "unpriced":0}}}
    Every value is a number, a model ID, a surface key, or a timestamp. Nothing else is possible by construction. Decoding ignores unknown keys and skips an undecodable line, such as a partial last line after a crash.
  • Write policy: the estimator needs the poll before and the poll at each utilization step, not every poll. Hold the newest unwritten record as pending. For each new record R:
    1. If R starts a new window, flush pending to its own window file, then write R.
    2. Otherwise, if round(weeklyPct) or surfaceShares changed since the previous observation, flush pending, then write R.
    3. Otherwise, if 30 minutes or more have passed since the last write, write R as a heartbeat.
    4. Otherwise R replaces pending.
    That is about 2 records per point plus a heartbeat every 30 minutes, roughly 450–550 records and 300–450 KB per heavy week, against about 2.5 MB if every 2-minute poll were logged. At launch, the last written record is read back from the current window's file.
  • Shadow readings: calibration/readings.jsonl gets one line each time the reading changes, which is at most once per new tick, about 80 lines a week. Fields: {evaluatedAt, windowStart, spanLower, spanUpper, kThis, kLast, ratio, ratioEqualPrices, ratioNonRead, ratioAtMinus10, ccPointsThis, ccPointsLast, localDollarsThis, localDollarsLast, readShareThis, readShareLast, shareThis, shareLast, mixTVD, ticksThis, ticksLast, gapShareThis, gapShareLast, shown, hiddenReason}. Shadow evaluation uses Config.shadow: G3 at 20%, G4 at 20 ticks, and G13 recorded rather than applied. Any other failing gate is recorded as hiddenReason, with the ratio whenever it can still be computed. ratioNonRead is the same rate using only non-cache-read dollars (§4.2).
    What they can and cannot tune. Four weeks give three week pairs. That is enough to see how far readings at 20%, 30%, and 50% drift from each week's final reading, and so to tune G3, G13, and the 50% early-read cut-off. readShare and ratioNonRead let a follow-up fit whether the plan counts cache reads at list price (§11). They cannot tune the 10% “similar” band: that needs the spread of final readings in weeks with no real change, and nothing labels which weeks those are. The band stays a judgment call.
  • A second writer, such as the dev ClaudeUsageDaemon running beside the app, adds interleaved records tagged with its own writer. Each line is written with a single append. The estimator evaluates one writer's series per window (§4.2), because token deltas taken across two writers would double-count.

6.5 CapEstimator.swift (new, Core, pure)

public enum CapEstimator {
    public struct Config { /* every §5 threshold, with the defaults above */ }
    public static func evaluate(this: [CalibrationRecord], last: [CalibrationRecord],
                                prices: PriceHistory, config: Config = .init()) -> BudgetComparison
}
public enum BudgetComparison: Equatable { case trend(BudgetTrend), hidden(HiddenReason) }
public struct BudgetTrend: Equatable {
    public enum Direction: Equatable { case same, down, up }
    public enum Reading: Equatable { case same, down(Int), up(Int) }
    public enum Note: Equatable {                 // tooltip sentences, in §3 order
        case earlyRead(spanUpperPct: Int)
        case pricesChanged(equalPrices: Reading)
        case modelMixChanged(lastTop: String?, thisTop: String?)   // display names, only when the top model differs
        case cacheReadShareChanged(thisPct: Int, lastPct: Int)
        case partialCoverage(thisPct: Int, lastPct: Int)
    }
    public let direction: Direction
    public let displayPct: Int      // N from reading(r) in §3; 0 for .same
    public let approximate: Bool    // shows “~”: N < 20, or an early read
    public let emphasized: Bool     // down, 20% or more, span reaches 50%
    public let spanUpperPct: Int    // S for the tooltip, e.g. 64
    public let ratio: Double        // raw k_this / k_last, for logs
    public let notes: [Note]
}

Config.display holds the §5 thresholds. Config.shadow differs only in G3 (20%), G4 (20 ticks), and G13 (recorded, not applied). The records' stored cost is not used. prices is used to rebuild cost from each record's token counts (§4.2), for the equal-price reading, for priceChanged, and for the display names in the model-mix note. The estimator has no I/O, clock, or global state; the price history is passed in. Every gate is unit-testable with synthetic records.

6.6 EngineState.swift and UsageEngine.swift

  • EngineState gains budgetTrend: BudgetTrend?, with a default value on the initializer so existing call sites (PopoverSampleRenderer, .empty) keep compiling.
  • On launch: load the current window's file (the newest file whose windowStart + 7d is later than now) and the file for the window before it, evaluate, and include the result in the first publish. The line paints from disk immediately, like the cached snapshot. No transcript scan is needed for this.
  • After each successful poll: publish(.ok) first, unchanged, so the usage display never waits on the scan. Then:
    1. If seven_day.resets_at is present, compute windowStart. Cross-check it against seven_day_breakdown.window_started_at. If they differ by more than 60 s, log one warning per window (this settles CLU-3 open question 5). The resets_at-derived start is always the one used.
    2. If the last pricing attempt was 24 hours or more ago (or 1 hour or more after a failure), run PricingFetcher and update PriceHistory (§6.2).
    3. await scanner.usage(since: windowStart, upTo: snapshot.capturedAt, prices: history).
    4. Build the record and pass it to CalibrationLog.
    5. Only if a record was written, since ticks change only on writes: re-evaluate with Config.display and, if the result changed, log it and publish again with the same status. Also evaluate with Config.shadow and append to readings.jsonl if that reading changed.
  • A failure in any of these steps (pricing fetch, scan, log I/O, decode) is logged and leaves budgetTrend unchanged or nil. It never changes EngineStatus, the back-off, or the snapshot.
  • When the window key changes, the scanner resets. The new week then has no ticks, so the line disappears until it passes 30% and settles.

7. Privacy and performance

  • Transcripts are sensitive. They contain full prompts and tool output. The scanner's decode types have no content fields, nothing from a transcript line is logged, and the calibration record has no free-text field. Log.redact still applies to all log lines.
  • Nothing about the user leaves the machine. There is one new outbound request: a daily GET of Anthropic's public pricing page, with no Authorization header, no cookies, and no query parameters. The usage endpoint is still the only request that carries the token.
  • Cost per poll: an incremental scan should finish in about 100 ms or less on this machine. A cold scan of one window at launch or rollover should finish in 2 s or less (the spike's full six-week scan took 0.73 s in Python). Log the duration of cold scans and of any scan over 250 ms. Neither may block the main actor.
  • Memory: one dedup map for the current window, about 2–8k entries of fixed-size numbers.

10. Out of scope

  • An absolute dollar value for the limit (“this week's limit is worth ≈ $850 of API usage”). This is the first half of the owner's question, “how much subsidized usage am I getting?”. The estimate is biased below about 70% utilization (CLU-3 §11), so it needs its own, stricter gate. It is a natural follow-up ticket, and nothing here blocks it: the calibration records already hold everything it needs.
  • Backfill from claude-usage.log (decision in §2).
  • Session-window estimates. The 5-hour window is too small and lags too much to divide by (CLU-3 §8).
  • Decoding extra_usage, limit_dollars, and used_dollars. A matched span stops at or below 99.5%, so spend beyond the limit never enters a tick, and the “exclude maxed-out windows” rule applies only to absolute estimates. Candidate follow-up.
  • Per-model weighting fits, testing how cache reads are weighted, and OpenTelemetry ingestion. The calibration log keeps the data these would need. If shadow readings confirm that the plan discounts cache reads (§11), changing the headline to weight them differently is its own follow-up.
  • Price modifiers from other sections of the pricing page (batch, long context, data residency). Claude Code's plan traffic is standard interactive traffic, which matched the §5 oracle exactly.
  • A setting to hide the line, and any icon change.

11. Risks and tunables

Watch these
  • Uneven weeks mislead early readings. A reading's random error is a few percent; its systematic error comes from how the week's work is spread across the span, and in the one real week that exceeded 100% at a 30% span. G13 keeps the worst of it off the screen but not all of it: the §5 replay would have shown “up 25%” on a Tuesday for a week that ended “similar”. How often this happens across ordinary weeks isn't known; the shadow readings measure it.
  • The plan may not count cache reads at list price. In the week of 2026-09-18, local cost per point from non-cache-read tokens was flat across 10-point bands ($2.08, 2.50, 2.37, 2.70), while cost per point from cache reads swung from $2.5 to $17.7. A fit of points against both gave cache reads about 0.09 of the weight of other dollars. If that holds, the headline moves with the share of cache reads in a week's work: going from 63% to 87%, the shares of two weeks in the spike, would read about “up 105%” with no change to the plan. This is one week and is confounded by off-Mac usage, so it is suggestive, not proven. The cache-read note (§3) flags it, and ratioNonRead in shadow readings lets a follow-up decide whether the headline should weight cache reads differently.
  • Claude Code on the web is invisible here, and appears to be counted as Claude Code. In the week of 2026-09-18, the first 20 points came with $0.07 of local spend, yet the endpoint later reported 94% Claude Code at 48%. At most about 3 of those 48 points were other surfaces, so at least about 17 points of “Claude Code” usage never reached this Mac, which is consistent with web sessions being folded into claude_code. The §6.1 check should confirm it. When that happens, moving work between web and this Mac shifts a full-span reading by about the same proportion, and an early reading by up to the whole span, since in that week 20 of the first 30 points were off this Mac. Running sessions in the CLI, VS Code, or the Desktop app, which all write local transcripts, keeps the measurement honest.
  • Thresholds rest on one validated pair. The matched-span method agreed to 0.4% once, at a 47.5% span; re-deriving the same pair gave $7.73 against the spike's $7.99, a 3% difference from tick-counting convention alone. The display thresholds are provisional. Revisit them after about four weeks of shadow readings (§6.4).
  • Switching models moves the number. Opus 5 → Opus 5.5 is happening on this machine now. The line shows it with a model-mix note rather than hiding, so a “down ~15%” during a switch may come from the switch, not the plan.
  • Price changes register late. A change takes effect in the history when the daily fetch first sees it, up to about 24 hours after the real change. With spend spread evenly, a missed day of a 20% change skews a week by about 3%. Spend is rarely even: in the week of 2026-09-18, 71% of local spend fell on one day, and a 20% change detected a day late on that day would skew the week by about 14%, into the “~15%” range. The price note (§3) fires whenever a change was detected inside either window, so such a reading is never unexplained.
  • The pricing page is a docs page, not an API. A layout change breaks the parser. The whole fetch is rejected, the last good table is kept, the log says why, and G12 hides the line after 7 days, so a silently wrong subsidy is never shown.
  • Fast-mode plan accounting is unknown. G8 covers it.
  • Undocumented surfaces. The breakdown can disappear (G6 hides the line) and the transcript format can drift (the scanner tests and G10's sanity checks catch it).
  • Other invisible usage (Cowork, chat, another Mac) is corrected for only through the endpoint's share. Between 25% and 90% the line shows with a note; below 25% it hides.

12. When the line first appears

Recording starts on first launch of the build that includes this feature. With G2 removed, a partly recorded first week can serve as “last week”, provided the next week overlaps it by at least 30 points (G4). If the build ships before the 2026-09-25 reset, that week is recorded in full, and the line can first appear in the week starting 2026-10-02, once it passes 30% and its reading has settled (G13). Replaying the week of 2026-09-18, that would have been around Tuesday. If the build ships mid-week, the first comparison may take one extra week. Shadow readings start on day one either way. Until the line appears, the panel looks exactly as it does today.
